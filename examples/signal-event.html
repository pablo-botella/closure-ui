closure-ui — <signal-event>

Demo of the one-shot signal element: the plain event dispatch, the storage directives (type="session-storage-set", -clear, -clear-wild and their local-storage- twins), the redirect directive, the <ss:key> / <ls:key> macros and the if-ss / if-not-ss conditions.

Every button below injects a <signal-event> into the page (the markup it injects is printed next to it) — the element fires once and removes itself, exactly as it would when written by the server. The page needs no server: sessionStorage works from file:// too. Open the browser console as well: unknown types and missing macro keys log a console.warn.

1. Plain event (the original behaviour)

A named CustomEvent dispatched on document, every data-* in event.detail; delay makes it a timer; target-id aims one element.

2. type="session-storage-set"

Every data-* pair is written to the storage (prefix stripped, kebab-case kept). The same element may also carry a name: the directive runs first, then the event.

3. type="session-storage-clear" and -clear-wild

key="a,b" removes those keys; without key nothing is removed (a warning). -clear-wild removes the keys matching the pattern globs (*, ?, anchored); pattern="*" is the deliberate way to empty a storage.

4. Macros <ss:key> / <ls:key>

Only with enable-macro="ss,ls"; a missing key logs a warning and nothing runs. Set sid in section 2 first.

5. Conditions if-ss / if-not-ss

Evaluated when the signal fires; a failed condition is a silent no-op.

6. type="redirect"

Navigates to url. history="replace" substitutes the current history entry (the page that carried the signal is gone from the history); the default push keeps it. With macros the url can carry a storage value, percent-encoded. Both buttons reload this page with a query string — check the Location line and the back button.

7. name="execute-template" → a <closure-template>

A signal dispatched at a template (its id) runs it as a button would: every data-* travels as a field, data-ct-role picks the role, the forms come from the enclosing <target-closure>. The template below posts to /api/soup (so this section needs the demo server: examples/server.exe, then http://localhost:8099/signal-event.html); the server answers a <closure-response sections> that fills the three slots and, for the starter, chains the main course with the directive twin, <response-item type="execute-template" … data-course="main">. The sid field is a <template-field enable-macro="ss">: set it in section 2 first, or watch the console warn and the request go without it.

8. The pattern: answer to an entry POST

The server answers an entry POST (a login, a hand-off from another site) with a page that stores the session id and sends the browser, without a trace in the history, to the first screen:

<signal-event type="session-storage-set" data-sid="tomato-soup-42"></signal-event>
<signal-event type="redirect" history="replace" enable-macro="ss"
              url="/kitchen/?sid=<ss:sid>"></signal-event>
